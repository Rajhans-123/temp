1 Introduction and Architecture

1.1 What the project does

The dataset holds two tables that describe the same thing from opposite sides: anime.csv describes 12,294 titles and ratings.csv holds 7,813,737 statements of taste from 73,515 users. Nothing in the raw data is clean, nothing is discrete enough to classify directly, and nothing is pre-computed for a model. The project therefore runs the full classical mining pipeline over it: clean and reshape the data, mine co-occurrence patterns, learn rules that classify a title's quality tier, estimate its score continuously, discover natural groupings in both the titles and the users, and finally ship a model that scores a new anime and recommends what to watch next.

1.2 End-to-end data flow

1.3 Why the output is CSV

Each stage writes flat tables rather than objects, which keeps the whole project inspectable with a text editor and makes it deployable without a database. Even the nested pipeline summaries are flattened to a long metric, value table (reports/mining_summary.csv), so there is no JSON anywhere in the data path. Only the two trained models are pickled, because a fitted scikit-learn estimator cannot be expressed as a table.

2 Stage 1 - Data Preprocessing

Cleaning is where a mining project is won or lost. Three properties of this dataset drive every decision below: rating = -1 means watched but not rated (1,476,496 rows), episodes is a text column containing "Unknown", and both members and episodes are badly right-skewed. Treating any of these as ordinary numbers silently corrupts every later stage.

2.1 Decisions and why they were made

rating = -1 (1,476,496 rows)Excluded as missing, not scored as a ratingIt encodes watched, not liked; scoring it would drag every mean down

Missing rating (230 rows)Type-wise mean, then global meanPreserves the per-type offset instead of flattening it

Handling of the 1 GB ratings file. The 7,813,737 rows are never loaded into memory: build_ratings_tables() streams them in 500,000-row chunks and keeps only running sums, sums of squares, maxima and minima. Peak memory stays flat and the stage finishes in about 13 seconds.

3 Stage 2 - Association Rules | Stage 3 - Classification

3.1 Association rule mining

Two rule bases are mined, because "which genres go together" and "what does someone watch after this" are different questions with different units of analysis. A genre basket treats each anime as a transaction whose items are its genres; a user basket treats each user as a transaction whose items are the titles they rated highly. Both directions of every pair are kept, because Mecha -> Action and Action -> Mecha share a lift but not a confidence.

Both Apriori and FP-Growth are implemented and benchmarked (core/association.py). They return identical itemsets at every threshold tested - 18 genre rules and 33 user rules at the default settings - which is the correctness check that matters. Every rule also carries conviction, leverage, Zhang's metric and Kulczynski's number, so it can be judged on more than lift alone.

Apriori versus FP-Growth. Both find exactly the same itemsets at every threshold tested (202, 112, 41, 22 at support 2%, 3%, 5%, 8%) - the correctness guarantee. Apriori is faster here because it scans only 5,501 short baskets; FP-Growth's advantage is asymptotic and both timings are reported.

3.2 Classification with J48 and Naive Bayes

The target rating is binned into four classes (Low, Medium, High, Top) at the 30/30/20/20 quantiles, giving 3,566 Low, 3,502 Medium, 2,350 High and 2,474 Top titles. J48 is implemented from scratch in core/decision_tree.py over 12 attributes - 8 numeric plus type, primary_genre, members_band and episodes_band.

A second variant, Categorical NB over one-hot attributes, reaches 0.5443 / 0.5112 in its own harness, so it is kept out of the shared-encoding table. The forest adds 28.7 accuracy points over the baseline; gain-ratio ranks is_shoujo, members_band, is_shounen, members and episodes_band on top, so community size and genre define the tier while episode count barely does. J48 lands within 0.027 of the forest while still producing 27 readable IF/THEN rules - extracted knowledge rather than the last accuracy point.

A scoring bug found by cross-checking. The comparison harness ordinal-encoded the training and test frames independently, so every model was scored against category codes it had never seen. Fitting one mapping on train and reusing it for test moved Gaussian NB from 0.4451 to 0.4758, the tree from 0.5427 to 0.5628 and the forest from 0.5607 to 0.5864. The table is post-fix.

4 Stage 4 - Regression | Stage 5 - Clustering

4.1 Regression - estimating the score continuously

Classification bins the score and throws information away; regression keeps it. Six regressors share one 80/20 split.

Mean baseline0.98970.79731.0292-0.000113.66

Gradient boosting is the strongest single model; the ensembles reach R2 = 0.60 against a mean baseline of 0. Read honestly: popularity and genre explain about 60% of score variance, and the other 40% is quality no attribute here captures. Ridge is indistinguishable from plain linear regression at this sample size - shrinkage has nothing to shrink.

Error by media type shows where it is weak. TV, the largest group (n = 738), is also the most predictable at MAE 0.427; ONA is worst at 0.623 on 122 rows, with Movie between them at 0.555. The learning curve is still descending, so this stage needs more data next, not more hyper-parameter search.

A leak that was found and removed. An engineered feature engagement_index = members x rating / 1000 produced an impossible test R2 of 0.91: the feature contains the target, so the model was reading the answer from its input. It was deleted, and the honest figure is the 0.60 above. Every split in this project is therefore made before any transformation is fitted.

4.2 Clustering - two datasets, two algorithms

Both datasets follow one workflow: standardise, choose k, run K-Means, run Ward-linkage agglomerative clustering, profile the centroids, cross-tabulate.

DatasetRowsFeatureskK-Means silhouetteWard silhouettek chosen because
A - Anime (content)12,294640.34080.3097elbow(knee)=4, silhouette-max=3
B - Users (behaviour)69,600850.27640.2200elbow(knee)=5, silhouette-max=4

What the segments turned out to be

Centroid profiles are named from their own statistics, so labels describe rather than decorate. Dataset A splits along reach and reception: its strongest segment, blockbuster / acclaimed / long-form, averages 7.18 with 9.4 log-members against 5.92 for the two weak ones. Dataset B splits along volume and generosity: the largest segment (29,373 users) rates 8.40 over 59 titles, the heaviest raters (4,855) rate 7.86, and the cross-tab puts 100% of the light/generous segment in the top rating band.

How k was chosen, and why hierarchical runs on a sample

Three signals are reported for every k: the elbow (furthest point from the line joining the first and last inertia value), the maximised silhouette, and Calinski-Harabasz with Davies-Bouldin as checks. The two main signals disagree by exactly one cluster on both datasets (elbow(knee)=4, silhouette-max=3 for A, elbow(knee)=5, silhouette-max=4 for B); the elbow wins both times, because one fewer cluster merges two genuinely distinct groups - on A the two low-scoring segments differ sharply in episode length, on B it would merge two light rater tiers with opposite habits. Ward linkage needs the full n x n matrix (38 GB for 69,600 users), so hierarchical_cluster() fits a seeded 1,200-row subsample and keeps the whole merge tree - any k from 2 to 8 comes off one run.

5 Stage 6 - Prediction and Recommendation System

The final stage produces the two models the interface actually calls. Both are trained here, persisted, and then only read at serving time.

5.1 Score predictor

A Random Forest and a Gradient Boosting regressor are blended. The weight is fitted on a validation split carved out of the training data, never on the test set; both learners are then refitted on the full training split. On the untouched test set the blend reaches RMSE 0.6531 and R2 0.5973, slightly better than either learner alone, and the UI shows a 95% interval of score +/- 1.96 x RMSE so a prediction is never a bare number.

5.2 Hybrid recommender

"What should I watch next?" is answered by combining five signals that earlier stages already computed, so the recommender adds no training cost:

  1. Taste segment (0.30). K-Means over the 69,600 user profiles gives 5 segments; each segment's mean rating per genre is streamed out of the raw ratings.
  2. Media-type preference (0.18). The same per type, so a segment can prefer TV over movies.
  3. Community prior (0.20) and type-relative quality (0.18). The title's own score z-scored across candidates, and how far it sits above its type's average.
  4. Popularity and rules (0.14 + boost). A small log-popularity preference, plus the lift of any stage-2 rule whose antecedent matches the watch list.

The result is a defensible match_score with a why column - "Action: your segment rates it 8.4 vs community 7.9" - so a recommendation can be explained rather than asserted. 47,153 users with at least 20 ratings are eligible; 6,941 titles are candidates.

6.3 Honest limitations

  • Genre is the only textual signal. With no synopsis, studio or demographic attributes, roughly 40% of score variance is unreachable.
  • Hierarchical clustering is sampled. Its silhouette is measured on 1,200 rows, not the full 69,600, and is labelled as such everywhere it appears.
  • No offline ranking metric. The recommender is justified by its blend logic and explainability, not by a measured NDCG or hit-rate, because the raw data contains no held-out "next watch" sequence.
  • Class imbalance is inherent. Low is genuinely rarer than Medium, so macro-F1 rather than accuracy is the fair metric.

6.4 Reproducing the project

python -m pip install -r requirements.txt
python build_dataset.py      # stage 1  (~13 s)
python train.py              # stages 2-6 (~5 min)
python smoke_test.py         # headless UI check
streamlit run app.py         # http://localhost:8501

Deployment is a single Streamlit app with no database: about 50 MB with the models included. The 1 GB raw ratings file is excluded by .gitignore and is never read at serving time - the app falls back to the processed tables when it is absent.

6.5 Conclusion

All six requested stages are implemented, measured on held-out data and exposed through one interface. The two deliverables that go beyond a textbook pipeline are the honest reporting of the leaked-feature correction, and the fact that every number in this report is read from the pipeline's own CSV output rather than typed in - so the document and the code cannot disagree. The natural next step is a held-out sequential evaluation of the recommender, which this dataset's schema does not currently support.
